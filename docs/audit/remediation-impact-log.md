| 2026-05-17 | D-3 (WP9) — cross-shard list tail-drop fixed via safe-cursor | `SqlxTransactionRepository::list` now uses two-phase pagination per the audit recipe. Was `per_shard_limit = limit + ceil(limit/N)` (slack heuristic) + merge-sort-truncate — under bunching (one shard's slice is dense, another sparse) the truncated page could silently miss tail rows on the sparse shard that should have appeared on this page (D-3, audit prescribed option 2). Now `per_shard_limit = limit + 1`: each shard fetches `limit + 1` rows; the `(limit+1)`th row from each shard (when present) is a "tail probe"; the MAX `(created_at, id)` across probes is the **safe cursor** = the OLDEST tuple for which every shard's slice still has full coverage newer than it. After the usual merge-sort-truncate, any row whose `(created_at, id) ≤ safe_cursor` is in a range where at least one shard's coverage is incomplete — drop it so the client's next-page cursor (derived from the last returned row) is guaranteed safe. Shards that exhaust (return < `limit + 1`) do not contribute a probe — they cannot have more rows than they returned. New metric `transactions_list_tail_skew_dropped_total` counts rows dropped this way (described in `init_metrics`). | Data layer / correctness: eliminates the silent-data-loss page-boundary bug for cross-shard transaction listings (ledger). Under the typical even-distribution case the safe cursor is OLDER than the merged page's last kept row, so the new branch drops zero rows and behavior matches the prior code.
